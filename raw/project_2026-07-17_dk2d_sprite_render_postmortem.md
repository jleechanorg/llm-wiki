Root asked "why did you think it was acceptable" after seeing DK2D characters (Arion et al.) render as unrecognizable blobs, compared against [[worldai2d-trim-baseline-video]]. Two distinct findings, don't conflate them:

**Finding A — a genuinely bad, self-documented-as-inadequate asset exists but is (probably) dead code.** `packages/web/src/dragonknight/sprites/arion.png` (bundler-imported via `spriteAssets.ts`'s `SPRITE_URLS`, feeding a `RendererAssets`/`viewportRenderer.ts` path) is a 32x32 PNG produced by algorithmically downscaling a painterly 1024x1024 illustration (crop→pad→Lanczos→24-color palette snap). Its own generating milestone doc, `docs/plans/dragonknight-2d/ART_32x32_MILESTONE.md` (commit `7c8d05b5`, 2026-07-12 03:21), delivered an honest **FAIL**: "signature-element fidelity gate FAILS... Do not treat these PNGs as final production art... Recommend against greenlighting full cast production from this recipe alone." ~7 hours later, commit `57133a0b` wired these exact rejected PNGs into production as "real anchor PNGs" with no caveat in the commit message. `Viewport.tsx` marks the `RendererAssets` type this feeds as `@deprecated unused now that rendering routes through the game2d LPC engine; kept for prop-compat` — meaning this bad asset is likely NOT what's actually rendering on screen today, but the file/pipeline is still in the tree and should be deleted once confirmed truly dead (don't just leave it — a future session could resurrect it by accident).

**Finding B — the REAL live render path (game2dBridge → game2d/render.ts → `/assets/game/characters/<id>.png`) uses genuinely good source atlases, so the bug is downstream of the art.** `packages/web/public/assets/game/characters/arion.png` and `gratian.png` are real 576x256 (9 cols x 4 rows of 64x64) atlases — Arion's is a real walk-cycle sourced from grok-imagine-video footage (`arion_front_walk.mp4` etc, per `game2d/assets.ts`'s own doc comments, wc-0psb), Gratian's is a real single-still repeated across columns (an "approved plan" scope reduction for supporting cast, not a bug). Both look clean and consistent when viewed directly at native 64x64-per-frame resolution — NOT blobby. Yet the live captured gameplay (both the stale Jul-16 evidence videos AND a fresh capture this session) shows Arion as an unrecognizable small red blob next to a much more legible Gratian. **This discrepancy is unexplained and unverified as of 2026-07-17** — did not have time to trace the actual `drawFrame`/frame-crop math in `packages/web/src/game2d/render.ts` + the cover-zoom multiplier in `game2dBridge.ts:computeDkCoverZoomMultiplier` to find where a 64x64 clean frame becomes a blob on screen. Leading hypotheses, none yet confirmed: (a) sprite drawn at too small an on-screen size for the viewport's cover-zoom math given DK's tiny ~10x6 authored rooms vs game2d's native 48x36 procgen world, (b) a frame-index/crop-offset bug bleeding adjacent 64x64 cells together, (c) canvas image smoothing left on somewhere blurring a small crisp source into mush.

**Why this matters for process:** the actual failure isn't "shipped bad art" (Finding B's atlases are fine) — it's a **known, self-documented, unresolved rendering defect that nobody re-verified visually after the fix-the-container work (PRs #275/276/277) landed.** Multiple sessions optimized measurable gates (responsive sizing, HUD consolidation, pagination, audio slider) without re-opening the video and checking "does the actual character on screen look like the atlas it's supposedly drawn from." wc-7e1k (flat world), wc-dwy5 (world reads static), wc-z980 (i2v animation pipeline unverified), and wc-wqjz (presentation layer) were all already open/in-progress beads acknowledging pieces of this before this postmortem.

**How to apply:** before proposing any new sprite-generation work, first root-cause Finding B (the crop/scale bug) — the assets may already be adequate once correctly drawn. Don't re-generate art to fix a rendering bug. Delete Finding A's dead pipeline (`spriteAssets.ts`'s `SPRITE_URLS`/`arion.png` et al under `packages/web/src/dragonknight/sprites/`) only after confirming zero live callers. See the DK2D wc-wqjz.3 mission bead / STATE.md for the active fix-mission tracking this.

Bead `jleechan-93cf` (ez-gh-actions) added a workspace bind-mount to fix Colima disk churn. Its own written acceptance criteria required "run six concurrent real jobs through container turnover" and "observe at least 30 minutes of active churn" before being considered done — but the notes explicitly said "still open: acceptance criterion 1 ... not yet captured" while the feature was SIMULTANEOUSLY live in production config. The only pre-deploy evidence was a synthetic single-file write test ("a throwaway container run as uid 1001 can create/write files through a virtiofs-backed host mount"). That test passed and told the deploying agent nothing about real `tar`-based archive extraction, which is what actually broke (see [[mac-fleet-outage-causal-chain-2026-07-14]] Layer 6): symlinks inside extracted GitHub Actions tool archives corrupted on the new mount, breaking `setup-python`/`setup-node`/`setup-gcloud` at a 41% (13/32) job failure rate.

**Why it went undetected for 1-2 days, not minutes:** `doctor-runner` (this repo's fleet health tool) measures container *activity* — EXECUTING/IDLE-OK/IDLE-STARVED/DOWN — never job *outcome*. A fleet that is 100% busy and 100% failing every job it picks up reads as perfectly healthy under that taxonomy. This is a direct escalation of [[health-probes-report-activity-not-idleness]] (2026-07-09: "listening" vs "busy" was ambiguous) — now the SAME class of blind spot recurred one level up: "busy" vs "succeeding" is just as ambiguous as "listening" vs "busy" was, and nothing had been built yet to distinguish them. A `scripts/job_outcome_monitor.py` was subsequently built (commit 8a745e8) as the fix for this specific gap.

**Why:** unit tests (or a single synthetic write) prove code-level correctness, never real-world runtime correctness against Docker+virtiofs+actual-GitHub-Actions-extraction-behavior. A bead's own acceptance criteria are not decorative — "still open" in the notes must block calling the feature done, not just get logged alongside a live deploy. And activity-based health monitoring has a structural blind spot for outcome regressions: it will never see a fleet that runs busily and fails every job.

**How to apply:** (1) Before marking any production-runtime-change bead (anything touching `docker_backend.rs`'s container-start/mount path, or the equivalent in another repo) as done, verify its OWN stated acceptance criteria are actually met — "still open" plus "live in prod" is a contradiction, not a status. (2) Any fleet/service health check that only measures "is it running/busy" needs a paired outcome check ("is what it's doing succeeding") — build both together, not activity first and outcome later. (3) This generalizes past ezgha: any daemon/service change validated only by synthetic smoke tests, deployed with real acceptance criteria left explicitly unmet, is the same failure shape regardless of repo or language. Related: [[health-probes-report-activity-not-idleness]], [[mac-fleet-outage-causal-chain-2026-07-14]], bead jleechan-93cf, jleechan-yn2o (root-cause synthesis + fix), and the repo CLAUDE.md "Reproducibility discipline" + "production runtime change" sections added as a direct result of this incident.
